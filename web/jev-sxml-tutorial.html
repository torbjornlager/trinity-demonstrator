Jev semantic observations in Web Prolog

First build a complete Jev-backed Observe–Think–Act actor with ordinary Prolog. Then add SXML only when the meaning of an observation depends on interaction history.

Part I — Jev + an ordinary Web Prolog actor

natural-language input
↓
bounded Choice, Score and Noul questions to Jev
↓
typed probabilistic decision
↓
Trinity semantic observation
↓
ordinary Prolog clauses in a Web Prolog actor
↓
conversational or simulated action

Jev answers bounded semantic questions. The Trinity layer treats the resulting typed probabilistic decision as a semantic observation: ordinary Prolog data, not generated code or permission to perform an effect.

1. Jev setup

The node owner supplies the credential and explicitly enables the narrow deployment-assessment capability. Uploaded code can choose only the input text; it cannot choose the credential, endpoint, model, or question vocabulary.

WP_JEV_SERVICE=yes
TYPESAFE_API_KEY=...             # owner environment only

The current provider endpoint is POST https://api.typesafe.ai/v1/systemone, authenticated with a bearer token. Provider details are isolated in jev_http.pl because they may change independently of the architecture.

2. The lowest-level useful request

The client sends one state value and a map of named typed questions. A reduced request looks like:

{
  "model": "jev-latest",
  "state": {"message": "Please prepare a deployment"},
  "questions": {
    "intent": {
      "type": "choice",
      "instructions": "Which single intent best describes the message?",
      "criteria": {
        "request_deploy": "Ask to prepare or perform a deployment",
        "affirm": "Confirm, approve, agree, or say yes",
        "deny": "Reject, cancel, disagree, or say no",
        "status": "Ask for current deployment status",
        "other": "None of the other options is a good fit"
      }
    }
  }
}

The response identifies the concrete model, returns answers under the same names, and includes usage. Transport errors and malformed responses remain provider-layer errors; application code never inspects provider JSON fields directly.

3. Typed probabilistic decisions as Prolog data

The project-level jev_decide/3 abstraction expresses Jev Choice, Score and Noul questions as Prolog terms and binds their typed probabilistic decisions:

jev_decide(_{message:Text}, [
    choice(intent, "Which intent?", Criteria, Intent),
    score(urgency, "How urgent?", Levels, Urgency),
    noul(is_question, "Is this a question?", IsQuestion)
], RawResponse).

A successful call binds:

Intent     = choice(Symbol, Probabilities, Confidence)
Urgency    = score(Value, Legend, LevelProbabilities, Confidence)
IsQuestion = noul(YesProbability)

Choice retains its full alternative distribution. Score is a probability-weighted position on a zero-based rubric, not a normalised confidence. Noul is the probability of yes/true and has no second confidence value. The complete provider response is retained rather than silently discarding model, usage, or future extension fields.

4. Treat the decision as a semantic observation

Both stages consume exactly one application-facing shape:

observation(IntentChoice,
            UrgencyScore,
            QuestionNoul,
            provenance(RawResponse))

No usable semantic answer is represented separately:

unavailable(configuration)
unavailable(timeout)
unavailable(rate_limited)
unavailable(malformed_response)
unavailable(transport)

An unavailable assessment is not deny, other, or false.

5–6. Receive input, Think and Act

The Stage 1 actor is the whole agent. It observes through the node capability, chooses an action with ordinary clauses, and replies:

jev_agent_loop :-
    receive({
        say(From, Ref, Text) ->
            jev_observation(Text, Observation),
            jev_stage1_decision(Observation, Action, Reply),
            From ! agent_reply(Ref,
                      report(Text, Observation, action(Action), Reply)),
            jev_agent_loop;
        stop -> true
    }).

request_deploy prepares only a simulated preview; status reports that no real deployment exists. The main success path therefore does not yet need confirmation state.

?- jev_agent_spawn(Pid).
?- self(Me), $Pid ! say(Me, deploy, "Please prepare a deployment"),
   receive({agent_reply(deploy, Report) -> true},
           [timeout(20), on_timeout(fail)]).
?- self(Me), $Pid ! say(Me, status, "What is the deployment status?"),
   receive({agent_reply(status, Report) -> true},
           [timeout(20), on_timeout(fail)]).
?- $Pid ! stop.
Checkpoint. We already have a complete neuro-symbolic Observe–Think–Act agent. Nothing so far requires a statechart.

Part II — Why add SXML?

Now introduce a problem the stateless success path did not have: a later utterance may refer to an earlier conversational commitment.

7. A confident label still leaves a question

Jev may confidently map both yes and ja to the symbolic Choice affirm. But classification alone cannot answer: affirm what?

Interaction stateObservationBehavioural meaning
idleaffirmExplain that nothing awaits confirmation.
awaiting_confirmationaffirmConfirm the pending simulated proposal.
awaiting_confirmationdenyCancel and return to idle.

Ordinary Prolog could store this state. SXML becomes useful because it makes the protocol, permitted next moves, and later temporal extensions explicit.

8–9. Explicit state and the macrostep boundary

The Stage 2 gateway reuses the same jev_deployment_observation/2 capability and the same observation/4 term. It adds only a chart-owning actor and the correlated event envelope:

observed(From, Ref, OriginalText, Observation)

The ordering is important:

  1. the gateway receives natural language;
  2. external Jev inference completes outside the chart;
  3. the completed result is normalised;
  4. observed/4 enters SXML as one external event;
  5. the chart processes its macrostep to completion without HTTP I/O.

The serial gateway preserves arrival order but blocks its mailbox while Jev answers. That is acceptable here. A production version needing cancellation or concurrency would use correlated worker actors and an explicit obsolete-result policy.

?- jev_sxml_agent_spawn(Pid).

10. The same observation in two states

Affirm while idle

?- self(Me), $Pid ! say(Me, idle_yes, "yes"),
   receive({demo_reply(idle_yes, Report) -> true},
           [timeout(20), on_timeout(fail)]).

Expect action(explain_context) and transition(none).

Create a pending commitment

?- self(Me), $Pid ! say(Me, deploy, "Please prepare a deployment"),
   receive({demo_reply(deploy, Report) -> true},
           [timeout(20), on_timeout(fail)]).

The request_deploy observation enters awaiting_confirmation. No deployment occurs.

Affirm while awaiting confirmation

?- self(Me), $Pid ! say(Me, confirm, "yes"),
   receive({demo_reply(confirm, Report) -> true},
           [timeout(20), on_timeout(fail)]).

The same symbolic affirm now selects simulate_deploy(Proposal) and returns to idle. The proposal contains the reference, original request text, and intent saved when the chart entered awaiting_confirmation; the larger raw provider response is not retained in interaction state.

Denial cancels

Prepare another proposal with the preceding button, then:

?- self(Me), $Pid ! say(Me, cancel, "no"),
   receive({demo_reply(cancel, Report) -> true},
           [timeout(20), on_timeout(fail)]).

11. Uncertainty remains data

Both stages accept an intent winner only when Choice confidence is at least 0.70. This is an application-specific teaching value, not a universal or calibrated threshold.

?- self(Me), $Pid ! say(Me, ambiguous,
       "Yes, deploy it -- actually no, do not deploy it."),
   receive({demo_reply(ambiguous, Report) -> true},
           [timeout(20), on_timeout(fail)]).

The 2026-09-25 live probe returned deny with deny=0.74, other=0.24, request_deploy=0.02, and confidence 0.66. Exact results may change. The deterministic policy asks for clarification and leaves the chart state unchanged.

This is deterministic control over uncertain evidence, not probabilistic control flow. The chart does not branch into alternative probabilistic states.

12. Swedish below the observation boundary

Prepare a proposal, then try Swedish affirmation:

?- self(Me), $Pid ! say(Me, swedish, "ja"),
   receive({demo_reply(swedish, Report) -> true},
           [timeout(20), on_timeout(fail)]).

If the sensor produces affirm, the Prolog and SXML layers use the same clauses and transition as English yes. Likewise nej can produce deny. This is language independence of the symbolic interface; a few successful probes do not establish multilingual accuracy.
