The ISOTOPE mental model

N2 creates one private toplevel for the browser session and gives it a pid internally. The portal reuses that pid for later HTTP requests. From the programmer's point of view it behaves like a private, long-lived Prolog shell:

Retained stateWhat it means
Loaded predicates and dynamic factsSeparate calls can build on private knowledge.
Current answer continuationNext resumes the pending search instead of rerunning it from the beginning.
Output and promptsA computation can converse with the same client over several HTTP exchanges.

Start with the relational query used throughout the profile path:

?- append(Xs,Ys,[a,b,c]).

Use ;, the space bar or Next for further answers. The logical answers are unchanged; what changes is that the search itself has an addressable lifetime.

Build a private basket across several calls

Load a small program into the session. Its dynamic predicate will hold this client's basket:

:- dynamic basket_item/2.

basket_clear :-
    retractall(basket_item(_, _)).

basket_add(Name, Price) :-
    atom(Name), number(Price), Price >= 0,
    assertz(basket_item(Name, Price)).

basket_remove(Name) :-
    retract(basket_item(Name, _)).

basket_total(Total) :-
    findall(Price, basket_item(_, Price), Prices),
    prices_total(Prices, Total).

prices_total([], 0).
prices_total([Price|Prices], Total) :-
    prices_total(Prices, Rest),
    Total is Price + Rest.

Initialize it, then make three independent calls:

?- basket_clear.
?- basket_add(tea, 4).
?- basket_add(bread, 3), basket_add(cheese, 8).
?- basket_total(Total).
Expect. Total = 15. The fourth request can see updates made by the preceding requests because they addressed the same private toplevel. A different client gets a different session and does not share these facts.

Continuation state is not database state

Ask for basket entries one at a time:

?- basket_item(Name, Price).

Next resumes the retained search. Stop discards only that continuation. Prove the distinction by stopping before all answers have been shown and asking for the total again:

?- basket_total(Total).
Expect. The total remains 15. At most one answer continuation is current in a toplevel; starting another call replaces pending search state, but it does not erase loaded code or dynamic facts.

Interactive input and output

A retained session gives input and output somewhere to go. First produce output:

?- basket_total(Total), format('Basket total: ~w~n', [Total]).

Now let the running goal ask the client for a term:

?- read(Item), basket_add(Item, 1).
At the |: prompt, enter a complete Prolog term such as coffee. The original computation waits, receives the term, adds it, and then succeeds. ISOBASE has no retained conversation in which this prompt could live.

Stop, Abort and session lifetime

ActionEndsSurvives
StopThe pending answer continuationPrivate code, facts and future calls
AbortThe active or waiting computationThe toplevel can accept another call
Halt or reclamationThe complete private toplevelNo state addressed by its old pid

Start a deliberately non-terminating computation, then interrupt it:

?- repeat, fail.

The server timeout may win if it is configured very short. After either outcome, ask for the basket total again to confirm that the session remains usable.

Session hygiene. Private sessions consume server resources. A client should halt an abandoned session when the protocol supports it; otherwise the node eventually reclaims it. See the API tutorial for the complete lifecycle.

Where the actor boundary lies

The session is implemented by an actor internally, but the ISOTOPE language does not expose independent processes, pids or mailboxes. Try one representative ACTOR operation:

?- spawn(writeln(hello), Pid).
Expect a profile violation. Application-visible actor spawn, send, receive, monitoring, linking, server behaviours and statechart actors require ACTOR. The struck-out actor and SXML examples in the drawer make the same boundary visible.

When to choose ISOTOPE

ISOTOPE's main advantages are:

  • a private database and answer continuation across calls;
  • interactive input and output;
  • the ability to abort a running computation; and
  • ordinary HTTP infrastructure without a persistent WebSocket.

It suits interactive query services, private workspaces, shopping or configuration flows, notebooks and conversational tools that need memory, I/O or cancellable work across several calls, but do not need independently running processes or server-initiated messages.

Compared with ACTOR, its HTTP request/response contract is simpler. Compared with ISOBASE, it requires the server to retain sessions, the client to manage their pids, and polling to retrieve events. That can still be unnecessary machinery for independent, function-like queries.

You should now be able to explain: what belongs to a private toplevel; why stopping a search does not clear its database; how input can span HTTP exchanges; and why a session is still not an application-visible actor system.
