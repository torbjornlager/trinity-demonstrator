Web Prolog manual

This web edition of Appendix B specifies the common Web Prolog language and API contract. The node’s HTTP and WebSocket interfaces are specified separately in Appendix D of the book. Both references describe a design in progress: the rules stated here are requirements for conforming implementations, rather than an inventory of current implementation behaviour. Deployment and implementation guides document setup, capabilities and any remaining conformance gaps.

The classification shown beside each entry identifies the minimum public node profile in which the predicate is available, or another relevant execution context. ISOBASE provides general stateless Prolog calls, ISOTOPE adds persistent toplevel sessions, and ACTOR adds the full stateful actor-messaging model. The profiles are cumulative, so an entry marked isotope is also available in ACTOR. The classification concerns the client language, not predicates used internally to implement a profile. Entries additionally marked owner only are reserved for code running with node-owner authority and are not available to ordinary client code.

The draft interoperability baseline 0.1 links selected requirements to executable tests and a coverage matrix. It includes GNU Prolog at ISOBASE level; this does not imply ACTOR support or completion of its broader ISOBASE audit. Untested and unresolved behavior remains explicit rather than being counted as passing.

Each predicate entry has a stable anchor based on its indicator. For runtime setup, deployment and implementation differences, see the native SWI guide, Trealla guide, GNU ISOBASE guide and SWI-WASM guide. The service examples document application-specific text handling.

Common conventions

The language contract is independent of the host Prolog system and execution mechanism. Environmental capabilities, including persistence, inbound connectivity, DOM access and hard termination, are reported by runtime_property/1. They do not change predicate meanings or result formats.

A client context groups one client interaction and its descendants. The hosting environment establishes the context and its lifetime, for example for an interactive session or a stateless request. Local and remote child creation retain that association. At each node, ordinary names and promises are scoped to this context. Sharing authentication credentials does not by itself merge contexts; reuse across requests requires an explicitly retained client context. Ending one request or replacing one toplevel within an explicitly retained context does not close that context. A remote descendant returning to a node retains its original context association there; it does not acquire a new context merely because its transport or execution engine changes.

Closing a context ends admission to its ordinary-name and promise scopes. Late creation, publication or attachment cannot reopen the closed scopes. An attachment concurrent with closure either joins the still-open context or is rejected after closure; it must not join a context whose retirement has already been committed. Context closure and actor termination are distinct: closing these scopes does not by itself terminate surviving actors. Standalone execution has an environment-provided root context.

Operator declarations

Web Prolog uses the following operator declarations.

:- op(800, xfx, !).
:- op(1000, xfy, if).
:- op(200, xfx, @).

Thus @ binds more tightly than !, which binds more tightly than conjunction. The right-associative if has the same priority as the comma, so Pattern if A, B -> Body is read as (Pattern if (A, B)) -> Body. Parentheses around a conjunctive guard remain useful for readability.

URI values

Every API argument or option that takes a URI or node URL requires an atom, for example 'https://n3.example'. This rule applies consistently to RPC and promise destinations, source URIs, the node/1 spawn option, and the node component of a canonical pid. Strings, character lists, code lists, numbers and compound terms are not accepted as URI values. Callers constructing URI text in another representation must convert it to an atom before passing it to the API.

An uninstantiated URI value raises an instantiation error without binding it; a non-atom raises a type error with expected type atom. Validation precedes source fetching, actor creation or request dispatch, as appropriate.

Requiring an atom does not introduce URI resolution, case-folding, escaping or fetch permissions. URI syntax, schemes, ports, relative paths, file access and origin restrictions remain subject to each entry’s resolution and fetch policy. An atom need not denote an allowed or reachable URI.

Options and validation

A Boolean option takes the atom true or false. This applies to link/1, monitor/1, session/1, trace/1 and once/1.

Option lists must be proper lists of recognised options with the documented arities and values. Every occurrence is validated, including later duplicates. The first occurrence of a scalar option determines its setting; repeated source options are additive. These rules apply to the creation predicates, toplevel calls and their synchronous wrappers, first_solution/3, rpc/3, promise/4 and yield/3.

Validation preserves shared variables and does not bind uninstantiated option values or execute goals or callbacks. It completes before source fetching, actor creation, request dispatch or promise collection, as appropriate. An invalid yield/3 option leaves the promise available for retry.

Errors have the form error(Formal, Context). A required value that is uninstantiated raises instantiation_error; a value of the wrong type raises type_error(ExpectedType, Value); and a value of the required type outside the permitted domain raises domain_error(Domain, Value). Boolean values have type atom and domain boolean. An unknown option or an option with an incorrect arity raises a domain error identifying the API’s option family. The Context argument supplies diagnostic information and is not part of the portable contract. Internal implementation metadata is not a public option.

Transport endpoints decode their wire representations before invoking the language API. Transport decoding is specified separately in Appendix D of the book.

Source loading

Source options are processed from left to right in option-list order, regardless of source kind. Clause order is preserved within each source text, clause list or copied predicate. Repeated clause-source options are additive; repeated URIs are fetched separately at each occurrence. An entry requiring exactly one initial document, such as statechart_spawn/2, rejects multiple document sources instead of combining them. All source is loaded before the goal runs and remains private to the receiving actor or stateless call. A source-loading failure prevents the goal from starting.

The caller prepares source before local execution or remote dispatch. For URI source, the caller fetches the contents and supplies them to the destination in the position specified by the option list. This rule applies to local and remote actor creation, RPC and promises. A promise completes source preparation before starting its asynchronous request and returning its reference; preparation errors are raised by the promise call itself.

The caller also fetches the initial statechart XML when it is supplied by URI and passes the document to the engine or node that will run the chart. The document’s URI is preserved as the base for resolving relative references. Any later document fetch explicitly requested by the running chart takes place in that chart’s execution environment.

URI resolution and fetching follow the caller’s access restrictions, including file-access permissions, origin restrictions and CORS where applicable. Relative source URIs are resolved in the caller’s environment, not against the destination’s public URL. Loading and execution follow the destination’s profile and sandbox; sender module names grant no authority.

Source text may be supplied as an atom or a string. Source predicates are identified by atom names and nonnegative integer arities.

Predicates for programming with core actors

Predicate: self/1
actor
self(-Pid) is det.

Binds Pid to the process identifier of the calling process.
Note: A pid is an actor address whose canonical global form is Id@Node, where Id is assigned by Node. This ordinary Prolog compound is part of the language contract: programs may copy, store, construct, decompose, compare, and serialise it. A shell may omit @Node when displaying a pid on the shell’s own node, but this is only a local abbreviation. Constructing a pid does not create an actor, confirm that it is live, or grant access to it; an operation reaches an actor only when the pair designates that actor and the node authorises the operation. Arithmetic on a numeric Id has no defined actor-level meaning. Web Prolog runtimes reserve localhost as the local-node designator. Passing such a pid across a node boundary requires preserving its originating routing context; it must not be reinterpreted as an address on the receiving node. Actor identifiers carry no host-engine or placement semantics.

In the browser, the main actor has pid main@localhost. Other local browser actors have pids of the form Id@localhost.

Predicate: spawn/1-3
actor
spawn(+Goal) is det.
spawn(+Goal, -Pid) is det.
spawn(+Goal, -Pid, +Options) is det.

Creates a new Web Prolog actor process running a copy of Goal. The new actor’s pid is unified with Pid before Goal is copied. If the same variable occurs in Goal and the pid argument, those occurrences therefore carry the child’s pid in the copy. Variables occurring more than once in Goal retain that sharing within the copy, but no variable identity is shared between the parent and child: bindings produced by the child do not bind variables in the parent, and subsequent parent bindings do not bind variables in the child. These rules are the same for local and remote spawning. Results that must cross the process boundary have to be returned explicitly, for example in a message or through a toplevel protocol.

Admission charges the principal’s whole locally hosted subtree. At the actor or CPU quota, spawning raises error(resource_error(actors),Context) or error(resource_error(cpu),Context). A non-owner’s link(false) raises:

error(permission_error(spawn, detached_actor, link(false)),
      Context)

Loss of the transport during a remote spawn raises:

error(remote_spawn_failed(connection_closed), Context)

The remote outcome is unknown, so a retry of effectful work requires application duplicate suppression.

Valid options are:

  • node(+URI)
    Creates the process locally or on a remote compatible node. Default is localhost.

  • monitor(+Boolean)
    If true, monitoring is installed as part of process creation. Default is false.

  • link(+Boolean)
    If true, installs directional parent-to-child link cleanup. Default is true. Only node owners may use false; detaching rehomes the actor under the node and sends its output to the node log.

  • src_text(+AtomOrString)
    Loads the clauses specified by a Web Prolog source text into the actor’s private Prolog database before calling Goal.

  • src_list(+ListOfClauses)
    Converts the clauses to source text and loads them into the actor’s private Prolog database before calling Goal.

  • src_uri(+URI)
    Loads the clauses specified by a file path, file URI, or HTTP(S) URI into the actor’s private Prolog database before calling Goal. The caller resolves and fetches the URI atom before creation or remote dispatch; sources are loaded in option-list order. See Source loading.

  • src_predicates(+ListOfPredicateIndicators)
    Loads the local predicates denoted by ListOfPredicateIndicators into the actor’s private Prolog database before calling Goal.

Note: In spawn(+Goal, -Pid, +Options), the option monitor(true) installs monitoring as part of process creation. When the child terminates, the parent receives a message down(Pid, Ref, Reason) where Pid is the terminated actor, Reason is its exit reason, and Ref identifies the monitor instance. For monitoring created via monitor(true), the portable contract is Ref = Pid; this lets the spawning process identify and remove that monitor even though spawn/3 returns no separate monitor reference.
Down-reason contract: The third argument of down(Pid, Ref, Reason) uses the following portable vocabulary: true means that the actor goal succeeded; false means that it failed; exception(E) carries the public representation of the uncaught exception; an arbitrary nonvar term may be supplied explicitly through exit/1-2; and no_process means that the monitored target did not exist when the monitor was installed. The boundary reason connection_closed means that observation of a remote target was lost; it does not assert that the target terminated. For an uncaught error(Formal,Context), the monitor notification preserves Formal but replaces Context with an unbound variable. An undefined-procedure error also omits a private generated actor-module qualification. Other exit reasons are unchanged.
Note: The semantics of link(true) are directional: if a parent spawns a child with linking enabled, termination of the parent causes linked children to be terminated. The link does not imply symmetric bidirectional exit propagation, and the child cannot trap the termination. The same rule applies to local and remote children. Remote creation installs the link before activation, and loss of the owning connection causes the hosting node to request termination of its linked children. A partition may delay detection and cleanup; observation loss alone does not establish completed reclamation. See the book’s section on remote links and monitors.

Options follow the common validation rules in Options and validation. node/1 takes an atom; link/1 and monitor/1 take true or false. Source options follow Source loading. Plain spawn/3 does not accept name/1; the specialised creation predicates provide named creation.

Named creation reserves the caller’s ordinary name before starting the actor and publishes it only after successful setup. An occupied or pending name prevents creation; pending names are invisible to whereis/2 and cannot be cancelled by unregister/1. Failure or interruption releases the reservation and reclaims resources owned by that attempt. Publication guarantees neither continued liveness nor application readiness. A remote name is an alias in the caller’s namespace, not a registration on the destination. Both local and remote named creation publish the prepared actor before activating its application goal. Remote creation therefore requires a preparation acknowledgement and an activation step after caller-side publication. A failed preparation never publishes a name. See register/2 for namespace and alias lifetimes.

Named remote creation requires a correlated spawn acknowledgement. An uncorrelated peer is rejected with remote_spawn_failed(uncorrelated_spawn_reply). Peer negotiation and compatibility adapters are specified separately from this language contract. Connection loss can raise remote_spawn_failed(connection_closed) while leaving the remote outcome unknown. Cleanup can request termination of a known remote pid but cannot undo remote side effects or guarantee cancellation after connection loss.

Local target/1 and io_target/1 select actor I/O routing, with io_target/1 taking precedence. Public WebSocket creation retains the connection’s control of those routes. Validation follows Options and validation, and mixed-source ordering follows Source loading.

Predicate: actors/1
actor
actors(-Pids) is det.

Binds Pids to the list of actor pids visible from the current execution context. In ordinary public client execution, this means the current actor or toplevel together with any actors that have been spawned on behalf of the same client interaction. Actors belonging to other clients are not included.

Note: Outside public client execution, for example in node-owned runtime code or administrative code, actors/1 returns the pids of all active local actors on the node.

Predicate: monitor/2
actor
monitor(+PidOrName, -Ref) is det.

Installs a monitor and returns a fresh reference in Ref. The first argument may be a pid or a registered local name, subject to the same target policy as sending. Fresh references are single-use and provide correlation, not sender authentication. References are opaque and must not be constructed or interpreted by application code. When the monitored process terminates, the monitoring process receives a message of the form down(Pid, Ref, Reason). If observation of a remote target is lost, the runtime instead delivers the same form with Reason = connection_closed. This discharges the monitor without claiming that the target terminated; reconnection does not restore it automatically.

Spawn-time monitoring and additional monitors are independent, including private monitors used by synchronous waits. Each active reference receives its own termination notification; removing a private or explicit monitor does not suppress notifications for other references.

Note: Using monitor(true) in spawn/3 installs monitoring before the child can terminate, so its actual exit reason is observed. If monitor/2 is called after the target has already terminated, the runtime still discharges the monitor with down(Pid,Ref,no_process).

Predicate: demonitor/1-2
actor
demonitor(+Ref) is det.
demonitor(+Ref, +Options) is det.

Stops the calling actor’s monitor identified by Ref. An unknown reference or another actor’s reference has no effect. This is idempotent. There is only one valid option:

  • flush
    Non-blocking removal of all pending down(_, Ref, _) messages from the mailbox.

For a remote monitor, removal is confirmed before the operation returns or applies flush. If confirmation times out, the operation raises error(remote_demonitor_timeout(Pid), Context) and retains the local monitor record for retry. Once the connection has been declared closed, local withdrawal suffices because that connection can deliver no further notifications. A successful removal prevents later notifications for that reference; already queued notifications remain unless flush is used.

Predicate: register/2
actor
register(+Name, +Pid) is det.

Registers the actor identified by Pid under atom Name. A pid may have one ordinary name and, independently, one service name. An occupied name or already named pid is rejected; a missing or terminating local pid raises existence_error(process,Pid). Registering a remote pid does not establish that it is alive or install a monitor.

Ordinary names belong to the caller’s client context and are inherited by its descendants. The node-wide service namespace is separate. Closing a client context removes its registrations and pending reservations and rejects late publication; removing a name does not terminate its actor.

Local termination removes ordinary registrations. A remote alias is withdrawn on observed termination of its exact pid or closure of the connection through which that alias is maintained. Cleanup preserves aliases associated with other connections, names rebound to another pid, service names and unrelated monitors. Connection loss does not prove remote death. Without an observed event, explicit unregister/1 may still be needed.

An already named pid raises permission_error(register, process, Pid); an occupied name raises permission_error(register, actor_name, Name). These formal terms are wrapped in error(Formal,Context) as described in the common error contract. The same errors apply to pending name reservations and named creation; a rejected operation preserves the existing registration and does not create or publish a replacement actor. A closed context rejects late registration with permission_error(register, closed_namespace, Namespace).

Predicate: whereis/2
actor
whereis(+Name, -Pid) is det.

Binds Pid to the value registered under Name in the caller’s ordinary namespace, or to undefined if no such registration exists. Lookup does not establish that the actor is alive.

Predicate: unregister/1
actor
unregister(+Name) is det.

Removes the association in the caller’s ordinary namespace. The actor itself is not terminated. The operation is idempotent and succeeds without effect if Name is not registered in that namespace.

Predicate: register_service/2
actor, owner only
register_service(+Name, +Pid) is det.

Publishes the live local actor identified by Pid under Name in the node’s public service namespace. Name must be an atom, Pid must identify an actor on the publishing node, and there may be at most one published service with a given name on a node. If the name is already published, register_service/2 raises permission_error(register, service, Name), even when the existing entry denotes the same actor. Replacement is therefore explicit: the owner must first withdraw the old mapping.

The public service namespace is distinct from the ordinary registration namespace used by register/2; the same atom may occur in both without a collision. A qualified address Name@Node is resolved against the public service namespace of Node. whereis/2 consults only the ordinary namespace; owner-side code may inspect the service namespace with whereis_service/2.

Publication neither changes the actor’s links nor places it under supervision. In particular, register_service/2 does not detach the actor from its parent. When the actor terminates, the node controller removes the service mapping atomically, so a published name never remains bound to a dead pid. A supervisor that starts a replacement actor must publish that actor again under the stable name.

Only code executing with node-owner authority may call this predicate. A call by any other principal raises permission_error(register, service, Name). A non-atom Name raises type_error(atom, Name); a Pid that does not identify a live actor raises existence_error(process, Pid); and an attempt to publish an actor on another node raises permission_error(register, service, Pid).

Predicate: whereis_service/2
actor, owner only
whereis_service(+Name, -Pid) is det.

Binds Pid to the live local actor published as Name, or to undefined if no such service is published. This predicate inspects only the public service namespace. Only code executing with node-owner authority may call it; other callers receive:

permission_error(access, actor_service_registry,
                 whereis_service(Name, Pid))

A non-atom Name raises type_error(atom, Name).

Predicate: unregister_service/1
actor, owner only
unregister_service(+Name) is det.

Withdraws Name from the node’s public service namespace. This operation removes only the name; it neither terminates nor otherwise changes the actor that the name denoted. The operation is idempotent: if no published service called Name exists, it succeeds without effect.

Only code executing with node-owner authority may call this predicate. A call by any other principal raises permission_error(unregister, service, Name), and a non-atom Name raises type_error(atom, Name).

Predicate: exit/1
actor
exit(+Reason) is det.

Terminates the calling process with Reason. If termination of the calling process has already been committed, the call has no effect and the original reason stands.

Predicate: exit/2
actor
exit(+Pid, +Reason) is det.

Sends an untrappable termination signal to the process identified by Pid, using Reason as its exit reason. The signal is not a mailbox message. The target must belong to the caller’s ownership tree unless the caller is a node owner; otherwise the call raises error(permission_error(exit,actor,Pid),Context). Host thread numbers and aliases are not actor pids. For remote actors, the runtime routes this request through the remote node. Termination commits when the target first accepts a termination signal; the first reason committed is final, and later termination or abort signals have no further observable effect. The signal takes effect at the target’s next safe point, which some operations can delay; see the book’s section on actors talking to other actors.

Predicates: !/2, send/2-3
actor
+PidOrName ! +Message is det.
send(+PidOrName, +Message) is det.
send(+PidOrName, +Message, +Options) is det.

Sends Message to the mailbox of the process identified as PidOrName. PidOrName may be a local pid, a local registered name, a global pid of the form Id@Node, or a published service address of the form Name@Node. A global pid may be a value returned by the runtime or a term constructed directly from a known identifier and node; the two are equivalent. Qualified service addresses are resolved only through the destination node’s live service registry. If such a service is absent or the sender is not authorised to use it, the send succeeds without delivery and does not reveal which condition applied. By contrast, an unknown local registered name raises existence_error(actor_name,Name); a send to an unknown pid succeeds without delivery. Language-level sending is open subject to node policy; admission may raise resource_error(mailbox) or resource_error(term_depth). Valid options for send/3 are:

  • delay(+Number)
    Delays the sending by a specified number of seconds. Default is 0.

  • id(+ID)
    ID is a user-supplied identifier that can be used by cancel/1 to stop the sending from taking place.

Portable actor application messages are acyclic ordinary Prolog terms. Atoms, strings, numbers, variables, lists, and compound terms are portable. Each send constructs a fresh copy in the recipient: repeated occurrences of one variable remain shared within that copied message, but no variable identity is shared with the sender or with any separately sent message. There is consequently no distributed unification channel hidden in message passing. Attributed variables, streams, and other non-text blob values must be encoded explicitly by the application. A double-quoted literal denotes a string. The same message-term contract applies to local and remote sending; additional host-specific terms are outside the language.
Ordering: For one sender, messages sent repeatedly to the same pid are delivered in send order while one controller route remains in use. The same holds for one unchanged name binding during that routing epoch. There is no portable order across pid/name addressing, name rebinding, reconnects or rerouting, different senders, or messages and runtime signals. For delayed sends, ordering begins when the delayed operation actually emits the message. See the book’s section on uniform messaging across node boundaries.

Predicate: cancel/1
actor
cancel(+ID) is det.

Tries to cancel all delayed messages with the specified ID that were scheduled by the calling actor. Identifiers are actor-local: another actor may use the same ID without its delayed sends being affected. Cancellation is best-effort only, since a message may already have been sent by the time the call is made.

Predicate: output/1-2
actor
output(+Data) is det.
output(+Data, +Options) is det.

Sends a message output(Pid, Data) to the target process. Pid is the pid of the current process. Valid option:

  • target(+Pid)
    Send the message to Pid. Default is the parent process.

This is a convenience predicate for ordinary actor messaging. Terminal writes such as format/2 and writeln/1 instead use the inherited terminal I/O target described in the book’s section on terminal authority across node boundaries. Any actor may use !/2 to send any term to any process to which it has a pid.

Predicate: input/2-3
actor
input(+Prompt, -Data) is det.
input(+Prompt, -Data, +Options) is det.

Sends prompt(Pid,prompt_ref(Ref,Prompt)) to the target process and waits for a reply carrying the fresh reference Ref. Prompt may be any Prolog term. Pid is the pid of the current process. Data is bound to the reply supplied through respond/3. Valid option:

  • target(+Pid)
    Send the prompt message to Pid. Default is the current I/O target when one has been installed, or otherwise the parent process.

Predicate: respond/3
actor
respond(+Pid, +Ref, +Input) is det.

Sends Input to Pid in response to the prompt that supplied Ref. A reply for an earlier prompt cannot answer a later prompt, even when both prompts came from the same actor.
The ACTOR badges on output/1-2, input/2-3, and respond/3 describe their availability to client programs. ISOTOPE sessions provide standard I/O predicates such as read/1 and writeln/1; the runtime implements session I/O through internal actor communication without exposing these actor predicates to ISOTOPE clients.

Predicate: receive/1-2
actor
receive(+Clauses) is nondet.
receive(+Clauses, +Options) is nondet.

Waits for, selects, and consumes one message from the calling process’s mailbox. A call is single-message, but not necessarily single-solution. During one invocation it selects and consumes at most one message. Messages are considered in arrival order, and each message is tested against the receive clauses in textual order. The first message accepted by a clause is removed from the mailbox. This selection is committed: backtracking through the invocation never selects another message or another clause.

The selected clause body is ordinary Prolog code. The call as a whole therefore has the determinism of the fired body: a body may fail, succeed once, throw an exception, or yield several solutions. Choice points left by the body remain available, but they enumerate solutions of that same body; they do not inspect the mailbox again. The selected message remains consumed if the body fails or throws, and is not restored on backtracking. Thus the nondet declaration concerns the possible number of logical solutions, not the number of messages consumed by one invocation. For example, after one foo message has arrived, receive({foo -> member(X, [a,b])}) consumes that message once but can yield both X = a and X = b.

A cut executed in a selected clause body is scoped to that body, as if the body were invoked through call/1. It can prune choice points created since entry to the body, but it cannot prune choice points in the caller; nor does it alter the already committed message and clause selection.

Clauses has the following form:

{  Pattern1 [if Guard1] ->
         Body1 ;
   ...
   PatternN [if GuardN] ->
         BodyN
}

A clause accepts a message if its pattern matches the message and its optional guard succeeds. Matching is one-sided: the pattern must subsume the message, so matching may bind variables in the pattern but never binds variables that occur in the message. For a ground message this is the same as unification. A guard is an ordinary goal and is not restricted in this way; a guard that checks a correlation reference or a pid should test the value, for example with ==, rather than bind it. Candidate matching and guard evaluation use a tentative substitution. If matching or the guard fails, all bindings made while trying that candidate are discarded before the next clause or message is considered; the mailbox is not changed until a clause accepts. A guard is evaluated for its first solution only, as if by once/1. Bindings from the successful pattern and guard are in scope in the body.

For portable code, a guard must be observationally free of side effects; the runtime is not required to enforce this restriction, and effects performed by a non-conforming guard are not undone when that guard fails. If a guard raises an ordinary exception, the exception and its tentative bindings are discarded and the clause does not accept the message. Control exceptions (abort, termination, and the enforced running-time limit; see the book’s section on actors talking to other actors) are not discarded: they propagate out of receive/1-2, and the message being examined remains in the mailbox in its original position. This error-as-non-match rule follows the selection discipline of restricted actor guards, but it also means that a guard which calls a fallible external service should translate failures into explicit results when the actor needs to distinguish them from an ordinary non-match.

Messages accepted by no clause are deferred: they remain in the mailbox, without any change in their contents or relative order, and are available to later receive calls. receive({}) accepts no message and waits, subject to Options. Valid options for receive/2 are:

  • timeout(+Number)
    Bounds the wait for an accepted message, in seconds. The value 0 inspects messages already in the mailbox without waiting for another. A positive timeout is converted once to an absolute deadline, so messages skipped during the scan do not restart the timeout. Default is no timeout.

  • deadline(+AbsoluteTime)
    Sets an absolute deadline in the same time scale as get_time/1. This is useful when several operations must share one time budget. A deadline that has already passed expires immediately. If both timeout/1 and deadline/1 are present, timeout/1 takes precedence.

  • on_timeout(+Goal)
    Called if the relative timeout or absolute deadline expires with no message accepted. Its success, failure, exception, and any choice points determine the outcome of the receive on the timeout path. Default is true. This option is only meaningful when timeout/1 or deadline/1 is present.

Predicate: flush/0
actor
flush is det.

Removes all messages currently pending in the mailbox of the calling process. Each removed message is rendered through the actor terminal-output path as a line of the form Shell got Message, where Message is the full Prolog term.

Note: flush/0 is primarily a shell-level inspection utility. It does not wait for future messages: once the mailbox is empty at the time of the call, it succeeds immediately.

Predicate: listing/0-1
isotope
listing is det.
listing(+What) is det.

listing/0 lists the content of the private database of the current actor process through the terminal-output path. Imported predicates and the injected I/O wrapper predicates are omitted.

listing/1 lists the predicates or clauses in the current process’s private database selected by What, following the conventional Prolog meaning of listing/1. What may be a predicate indicator (Name/Arity or Name//Arity), a callable head pattern, a clause reference, or a list of such specifications. It does not provide access to another actor’s private database.

Predicates for programming with toplevel actors

Predicate: toplevel_spawn/1-2
actor
toplevel_spawn(-Pid) is det.
toplevel_spawn(-Pid, +Options) is det.

Spawns a toplevel actor and binds Pid to its pid. All options accepted by spawn/3 are also accepted by toplevel_spawn/2. URI fetching follows Source loading, as for spawn/3. In addition, toplevel_spawn/2 accepts the following options:

  • session(+Boolean)
    If set to false, the toplevel actor terminates after having run a goal to completion. If true, further interaction is expected. Default is false in the actor API.

  • target(+Pid)
    Send all answer terms to Pid. Default is the pid of the parent.

Internal compatibility metadata is not a public option. Shared variables and the original restart specifications are retained.

A permanent child restarts after any termination, a transient child after failure or abnormal termination but not success (true), and a temporary child never restarts. one_for_one replaces the affected child; one_for_all restarts the whole group; rest_for_one restarts that child and later siblings. Replacements retain child order, dynamic additions append, successfully completed transient children retain an inactive specification, and temporary children are removed.

Startup rollback: Failed initial startup reclaims that attempt’s provisional children in reverse start order using their shutdown policies. A failed dynamic addition reclaims only its own provisional child and leaves existing siblings and supervisor state unchanged, allowing retry. These paths preserve unrelated monitors and messages, and cleanup errors do not replace the primary startup failure or prevent other cleanup attempts. An infinity shutdown policy may delay completion indefinitely. Startup here means creation, preparation and admission; a child terminating after successful creation follows its restart policy.

An ordinary initial startup failure has reason init_failed; an initial exception retains its original error term. Dynamic additions and explicit respawn return error(start_failed) for ordinary failure or error(Error) for an exception, leaving the supervisor available. Reserved runtime control transfers still propagate.

Restart failure: A failed explicit respawn rolls back only that attempt, retaining existing siblings and the inactive specification for retry. If an automatic replacement fails, provisional replacements are reclaimed, remaining children are stopped in reverse start order using their shutdown policies, and the supervisor exits with restart_failed(Id,Reason). Id identifies the replacement that failed; Reason is start_failed or its original exception. These paths preserve unrelated actors, monitors and messages; cleanup errors do not replace the primary failure or prevent other cleanup attempts.

Restart-intensity exhaustion: The restart budget is checked before replacement startup. Exhaustion starts no excess replacement, stops remaining recorded children in reverse start order using their shutdown policies, and exits with shutdown. An intensity(0) budget permits no automatic restarts. Cleanup preserves unrelated monitors and messages; ordinary cleanup errors do not replace the shutdown reason or prevent attempts to stop other children.

Startup completion: Creation returns successfully only after all initial child starts have completed creation, preparation and admission. This does not require their application goals to finish or establish application readiness. A failed initial start rolls back the provisional children and raises error(supervisor_start_failed(Pid, Reason), Context), where Reason is init_failed or the original exception. Failed named creation releases its reservation. Child application goals may run during supervisor setup, so rollback cannot undo their external effects.

Child shutdown policies govern explicit termination, normal halt, rollback and group-restart stopping. brutal_kill stops immediately with reason kill. A recognised server start receives a graceful stop request and is forced down with reason shutdown if its numeric timeout expires. Zero and fractional timeouts are supported. Plain actors and nested supervisors receive direct termination with reason shutdown; recursive cooperative shutdown is not guaranteed. A stop acknowledgement alone does not establish completed termination.

These guarantees require the runtime to execute its cleanup paths. Hard termination can bypass Prolog cleanup; losing a remote connection does not prove remote death, and an unacknowledged remote start can have an unknown outcome. No general guarantee is made here for cleanup after arbitrary supervisor exits. Synchronous request waits and their errors are described below.

Predicate: parallel/1
actor
parallel(+Goals) is semidet.

Runs the proper list of independent goals Goals concurrently, using one monitored worker actor per goal. The call succeeds when every goal has produced its first solution and returns the resulting variable bindings. parallel([]) succeeds immediately. Further solutions are not enumerated on backtracking.

The predicates parallel/1 and first_solution/2-3 can be called directly in an ACTOR toplevel, with or without supplied source. Worker goals may use predicates supplied in the caller’s source.

If any goal fails, the remaining workers are terminated and the call fails. If any goal throws an exception, the remaining workers are terminated and the exception is rethrown. If a worker terminates without a result for any other reason, including true, the remaining workers are terminated and worker_exit(Pid,Reason) is thrown. Once a worker’s result has been accepted, its termination notification only confirms that it has stopped. If several workers have abnormal outcomes, the first failure or error notification observed by parallel/1 determines the result; this selection may depend on scheduling and does not promise leftmost-goal precedence. Result and monitor messages belonging to the workers are removed before the predicate returns, fails, or throws.

Worker cleanup covers partial startup failure, exceptions, caller interruption and abandonment of the call. Only the combinator’s workers and their result/monitor messages are reclaimed; unrelated actors, monitors and messages are preserved. This is local cleanup and does not cancel remote computations already requested by a worker. A shell abort closes that shell’s combinator scopes; ordinary actors outside those scopes follow their own lifetime rules. Forced termination that bypasses runtime cleanup remains a limitation.

The goals must not depend on bindings or side effects produced by sibling goals. Actor creation and message copying add overhead, and the one-worker-per-goal model gives large goal lists a correspondingly large resource footprint.

A non-list Goals raises type_error(list, Goals). An element that is not callable raises the corresponding callable type error from its worker, which is propagated to the caller.

A non-list Goals or Options raises type_error(list,Term). Policy values must be atoms: a non-atom raises type_error(atom,Action), and an atom other than stop or continue raises domain_error(first_solution_policy,Action). An unknown or incorrectly aritied option raises domain_error(first_solution_option,Option). Every occurrence is checked and the first setting for each policy takes precedence.

The parallel/1 worker-cleanup and unexpected-exit rules also apply here. on_error/1 governs unexplained worker exits as well as exceptions. A winner is selected before output unification; even if the caller’s output does not match, remaining workers are cleaned up before the call fails.

Predicates for remote Prolog-style calls

Predicate: rpc/2-3
isobase
rpc(+URI, +Goal) is nondet.
rpc(+URI, +Goal, +Options) is nondet.

Executes a copy of Goal through the stateless /call endpoint of the node identified by URI, then unifies the local goal with each returned solution on backtracking. This remains a stateless call even when the destination is an ACTOR node: actor-only predicates such as self/1, spawn/1-3, and receive/1-2 are not available through rpc/2-3.

A stateless goal can itself call rpc/2-3 or create and collect a promise. The same profile, sandbox and client-context rules apply. A promise reference can be used across requests only if those requests retain the same client context at the creating node.

The first argument alone selects the execution node. localhost means the node on which rpc/2-3 is running. Source-loading options supply source for the call’s temporary private database. For example:

rpc('http://n2.org', Goal, [
   src_uri('http://n3.org')
])

executes Goal on n2.org. The caller fetches the source from n3.org and sends its text to n2.org, following Source loading. The options are:

  • limit(+Integer)
    Limits the solutions retrieved per roundtrip to a positive integer. If omitted, all solutions are requested. Exceeding an execution-time or result-size bound produces an error, not a truncated success response; the client may retry with a finite limit. Execution-time exhaustion is reported as error(resource_error(time),_); memory or result-size exhaustion as error(resource_error(space),_). The context argument is elided in normal display. RPC clients propagate the remote exception without an additional wrapper. A client transport timeout is a separate condition and does not establish that the remote computation has stopped.

  • once(+Boolean)
    When true, retrieves only the first slice and does not request later slices. Default is false.

  • timeout(+Number)
    Requests a timeout in seconds for goal execution on the destination node. The effective timeout is the minimum of this value and the node owner’s configured timeout.

  • http_timeout(+Number)
    Sets the client-side HTTP transport timeout in seconds for each request. It does not change the destination node’s execution timeout.

  • src_text(+AtomOrString)
    Loads source text into the temporary private database before calling Goal.

  • src_list(+ListOfClauses)
    Converts the clauses to source text and loads them into the temporary private database.

  • src_uri(+URI)
    Fetches source from URI and loads it into the temporary private database in option-list order. This URI atom is a source location only. The caller resolves and fetches it before dispatch, then sends source text to the execution node. Relative URIs use the caller’s context and source-access policy.

  • src_predicates(+ListOfPredicateIndicators)
    Copies the caller’s indicated predicates into the temporary private database.

The following HTTP transport options are also accepted. They affect the client’s requests to the execution node, including later slice requests; they do not configure source fetching or remote goal execution:

  • request_header(+Name=+Value)
    Adds a request header. Name is an atom and Value an atom or string. Several headers may be supplied as separate options; the first occurrence for each case-insensitive header name takes precedence and every occurrence is validated. Names must be nonempty HTTP field-name tokens; values must not contain line breaks or other control characters except horizontal tabs.

  • authorization(+Credentials)
    Sends HTTP credentials: basic(User,Password) or bearer(Token), with atom or string arguments.

  • user_agent(+Agent)
    Sets the HTTP user-agent value to the given atom or string.

Header values and credential arguments accept atoms, strings and proper lists of one-character atoms. Textual field values use UTF-8 on the wire. Basic credentials are encoded as UTF-8 before Base64 encoding. Header-name comparison also applies across option forms: authorization/1 supplies the Authorization field and user_agent/1 supplies User-Agent, so the first applicable option in list order wins.

Malformed header pairs raise type_error(http_request_header, Value); unsupported credential forms raise domain_error(http_authorization, Value). Text values of the wrong type raise type_error(atom_or_string, Value). Invalid field-name or field-value characters raise domain errors with domains http_header_name or http_header_value, respectively. An uninstantiated required component raises an instantiation error.

Only the documented transport options are accepted. Caller access policy, including browser restrictions on request fields and CORS, still applies. Request fields do not grant authority to assert trusted proxy identity; reserved identity fields raise permission_error(set, proxy_header, Name). An operator-bound credential may also prevent a caller from supplying a conflicting Authorization field.

Options follow the common validation rules in Options and validation. limit/1 is a positive integer; once/1 is boolean. Source options follow Source loading. template/1 and offset/1 belong to promise/4 and are rejected by rpc/3.

For rpc/3, every answer in the first slice remains available on backtracking; once(true) prevents subsequent page requests even if the peer reports more answers. The client forwards the setting to the destination, which finishes the computation after that slice and retains no continuation. This does not provide remote cancellation.

timeout/1 requests a destination-side execution timeout; http_timeout/1 sets the caller’s transport timeout. Both require numbers of seconds; negative values are normalised to zero. Omission leaves the corresponding default in effect. These are separate settings, each using its first occurrence, and every occurrence is validated before source preparation or dispatch.

The HTTP timeout bounds each complete request, including response headers and body, and starts afresh for each later slice. It does not bound caller-side source preparation, which follows Source loading. Exhaustion raises error(rpc_error(http_timeout),_) in rpc/3. A promise delivers the local exception as error(error(rpc_error(http_timeout),_)) through yield/2-3. This does not establish that the destination’s computation has stopped.

Predicate: promise/3-4
isobase
promise(+URI, +Goal, -Ref) is det.
promise(+URI, +Goal, -Ref, +Options) is det.

Starts one asynchronous stateless call to node URI with Goal and returns a local promise reference in Ref. As with rpc/2-3, the first argument selects the execution node and localhost denotes the current node. Source-loading options populate the promised call’s temporary private database; they do not change its execution node. The caller completes source preparation, including any src_uri/1 fetch, before returning Ref; errors at this stage are raised by promise/3-4 itself. The remote query runs asynchronously. It accepts the same limit/1, once/1, timeout/1, http_timeout/1, and src_*/1 options as rpc/3, together with:

  • template(+Template)
    Template is a term sharing variables with the goal. By default, the template is identical to the goal.

  • offset(+Integer)
    Selects the starting offset of the single solution slice collected by the promise. Default is 0.

The reference returned in Ref can later be used by yield/2-3 to collect the single answer term. Programs must not infer meaning from its digits or construct references themselves.

A promise always collects one slice. With once(true), it additionally asks the destination to finish the computation after that slice rather than retain a continuation; omission defaults to false. The complete peer answer, including its More flag, is returned unchanged. A local yield timeout does not change this setting or consume the promise.

Options use the same validation rules and HTTP transport options as rpc/3, plus arbitrary template/1 and nonnegative integer offset/1. Template variables remain shared with the goal, and the caller’s variables are not bound by remote execution. Collection, explicit disposal and five-minute expiry reclaim local promise resources; pending and ready but uncollected promises can expire. Late completion cannot recreate a disposed reference.

A promise is local to its creating node and belongs to the client context in which it was created. Its reference identifies it within that node and context independently of engine placement. Code running at that node on behalf of the same context may collect or dispose of it; code in another context cannot. Passing a reference to a remote node does not create a distributed promise or confer access to the originating node’s promise. Authentication alone does not grant access to another context’s promises. A client collecting across requests must retain its context explicitly. Ownership transfer is unsupported.

For example, suppose a client at node A creates a promise there and spawns a child at node B. A descendant of that child returning to A may collect the promise while the original context remains open. A separate client at A, even one using the same authentication credentials, cannot collect it. The reference alone grants neither access at A nor collection at B.

Closing the context disposes of all its pending and uncollected promises. This does not itself terminate surviving actors or cancel remote execution. Moving work between engines at the same node within a context must preserve reference identity and access rules. Numeric references must not be reused while an earlier reference could still designate a promise in that context.

Predicate: yield/2-3
isobase
yield(+Ref, -Answer) is det.
yield(+Ref, -Answer, +Options) is det.

Waits for the answer term from a previous call to promise/3-4. The reference is local to its creating node and client context. The contract is one collection of one answer term; backtracking does not enumerate further results. Timeout handling must return a defined answer term or throw an exception. Remote answers are success(Data,More), failure, or error(Error). If on_timeout/1 is omitted, the timeout path succeeds with Answer = timeout. A timeout callback may supply its own defined result. This wait outcome is distinct from remote logical failure or an error answer. yield/2 is equivalent to yield/3 with an empty option list. Valid options are:

  • timeout(+Number)
    Waits at most Number seconds for the promised answer. Default is no timeout.

  • on_timeout(+Goal)
    Calls Goal once in the caller’s context if the wait expires. It is not called when an answer is collected. Bindings it makes to Answer are retained; if Answer remains unbound, it is set to timeout. Callback failure throws error(timeout_callback_failed(Ref),_); an exception propagates. Callback alternatives do not become additional results of yield/3.

Options follow the common validation rules in Options and validation. timeout/1 requires a number and on_timeout/1 requires a callable goal. Callback context and sharing with Answer are preserved. A local producer failure is delivered as an error answer rather than leaving the collector blocked.

Only one collector may wait on a reference at a time; a competing yield raises permission_error(collect,promise,Ref). Timeout, cooperative interruption or an exception before collection commits releases the collector and retains the promise. Collection consumes the selected answer before output unification; a mismatch therefore fails without making the answer available again. Disposal or expiry wakes a waiting collector with existence_error(promise,Ref), without invoking its timeout callback. Access from another ownership scope is treated as a missing reference.

Completing one request or ending one toplevel within a retained client context does not dispose of that context’s promises. Closing the context wakes collectors with a missing-reference error and closes further admission, while surviving actors remain alive. A collection that commits first returns its answer; disposal that wins invalidates the reference. Timeout and retry remain possible only while the reference and its owner remain valid. Ownership transfer and guaranteed remote cancellation remain separate work in Appendix F of the book.

Predicate: promise_cleanup/1
isobase
promise_cleanup(+Ref) is det.

Disposes of the caller-accessible promise and its local resources. Ref must be an integer. Cleanup is idempotent for missing, consumed, expired, disposed or inaccessible references; a later yield raises existence_error(promise,Ref). The ownership boundaries under promise/3-4 apply. Disposing of local resources does not guarantee cancellation of execution on the remote node.

Predicate: runtime_property/1
isobase
runtime_property(?Property) is nondet.

Enumerates capabilities of the execution environment. These properties describe available facilities and lifetime constraints without changing the language contract. Defined properties are:

  • persistent(+Boolean)

  • inbound_addressable(+Boolean)

  • dom(+Boolean)

  • actor_isolation(independent|cooperative)

  • hard_termination(+Boolean)

Boolean property values are true or false. persistent/1 reports whether the environment can outlive the client page or interactive connection; inbound_addressable/1 reports whether it accepts incoming node connections; dom/1 reports access to the page DOM. actor_isolation/1 distinguishes independently scheduled actors from actors sharing a cooperative execution engine. hard_termination/1 reports whether an actor can be stopped without its cooperation. Hard termination does not guarantee execution of Prolog cleanup handlers. Source access may additionally be restricted by origin, CORS, file-access or other deployment policies.

An unbound argument enumerates the properties; unsupported properties and non-matching values fail. Implementation identity and host-engine details belong in diagnostic tools and deployment guides.

Common error contract

Predicate entries above state specialised errors where they matter. Standard Prolog exceptions have the form error(Formal,Context). The formal term identifies the condition. The context is implementation-defined. Portable handlers match the formal term and leave the context open, for example error(type_error(integer,Culprit),_). Registration conflicts use permission_error/3; missing required child start options use existence_error(option,start(Id)), retaining the child id in the portable formal term. These runtime failures are wrapped in error/2. An explicit throw(Term) can raise an application exception with any portable term shape, including an error/2 term with its own context. The common formal terms have the following roles:

FormMeaning
instantiation_errorA required input was insufficiently instantiated.
type_error/2The value has the wrong Prolog type; arguments identify the expected type and culprit.
domain_error/2The type is acceptable but the value is outside the operation’s domain.
existence_error/2A required process, procedure, source, or other object does not exist.
permission_error/3The operation is defined but not authorised in this execution context.
evaluation_error/1An arithmetic operation raised an exception, for example division by zero.
resource_error/1The runtime cannot supply a required bounded resource.
resource_error(time)A configured execution limit expired.

A direct predicate call throws the exception term. PTCP reports a submitted-goal error as error(Pid,E); stateless calls use error(E); HTTP and WebSocket bindings place its public representation in a type:"error" envelope. An uncaught actor exception is observed by a monitor as down(Pid,Ref,exception(E)). Boundary sanitisation may remove host-private context but must preserve the portable formal error in Prolog-format responses and node-to-node term fields. JSON diagnostic text may differ across nodes. The demonstrator displays concise prose by default. Enable Show exception terms under Settings → Terminal to display the Prolog exception with its context omitted, when the response supplies one. For programmatic classification use the Prolog term or a documented protocol code. Appendix D of the book specifies these representations and the available machine-readable error codes.

If admission rejects a submitted goal before execution starts, the submission interface reports the error. A catch/3 inside the goal can handle exceptions raised during its execution.

isobase
member(?Element, ?List) is nondet.

Unifies Element with successive elements of List, from left to right. Backtracking visits each position, including positions containing equal elements. With an uninstantiated list, it generates lists containing the element at successively later positions.

?- findall(X, member(X, [a,b,a]), Xs).
Xs = [a,b,a].

isobase

isobase

Traverses one to three lists from left to right, threading an accumulator. At each position, the callback receives the corresponding list elements in list-argument order, followed by the incoming and outgoing accumulators. Thus the one-list form calls call(Closure,Element,S0,S1); the next position receives S1 as its incoming accumulator. The last outgoing accumulator unifies with State. Executes Goal and numbers its successive answers from one, including equal answers reached by different alternatives. Predicate: countall/2
isobase
countall(+Goal, ?Count) is semidet.

Exhausts Goal and unifies Count with its number of answers, counting duplicates separately. A supplied non-negative integer count succeeds exactly when it equals that number. A failing goal has count zero. Bindings made while enumerating the goal do not escape; variables shared with Count are bound only by unification with the final count. Backtracking does not produce another count. An exception propagates without returning a partial count. A goal with infinitely many answers does not yield a completed count.

?- countall(member(X, [a,b,a]), N), var(X).
N = 3.
?- countall(fail, N).
N = 0.
Predicate: forall/2
isobase
forall(+Generate, ?Test) is semidet.

Requires Test to succeed for every answer of Generate. Each generator answer supplies bindings to its test; one successful test alternative is enough for that answer. The predicate fails as soon as a test has no successful alternative. Bindings made by either callback do not escape. If the generator has no answers, forall/2 succeeds without invoking the test. These rules also apply inside other meta-predicates. It has the same success and binding behaviour as:

\+ (call(Generate), \+ call(Test))

For example:

?- forall(member(X, [1,2,3]), X > 0), var(X).
true.
?- forall(fail, Unused), var(Unused).
true.

Remote execution and compatibility

A defined remote operation remains subject to the caller’s source-access policy, permission to use the destination, and the destination’s admission and execution policy. These are separate requirements: permission to fetch source does not grant permission to create an actor at that origin, and an allowed destination does not supply transport credentials. Retaining a client context across nodes does not widen any of these permissions. A deployment may restrict permitted peers without changing the operation’s language meaning.

Remote execution-time exhaustion is reported as error(resource_error(time), _), and memory exhaustion as error(resource_error(space), _). RPC clients propagate these exceptions. A client transport timeout does not establish that the remote computation has stopped.

Compatible peers preserve complete ordinary Prolog answer terms, variable sharing, quoted atoms, strings and exceptions. Public asynchronous answers remain success(Pid, Slice, More), failure(Pid) and error(Pid, Error). Missing or invalid term payloads raise remote_answer_protocol_error(missing_term) or remote_answer_protocol_error(invalid_term). Display text is not a substitute for a structured answer. Protocol negotiation and adapters for older peers are specified outside the language reference. This does not relax the message-term contract for send/2-3.

Monitor references retain their complete value, independently of pid display abbreviation. Correlated synchronous operations require peer support and fail explicitly when unavailable; peer compatibility is checked before dispatching operations that require it. A timeout or connection loss is not remote cancellation.

Page sizes are caller-controlled: HTTP requests, persistent-toplevel calls and next honour limit(N) without silently reducing it to an owner solution-count cap. A finite goal may finish with fewer answers; applicable resource limits still apply.

HTTP paging offsets advance by the number of answers actually returned, rather than the requested limit. A short non-final page therefore does not skip answers or a pending error. When an HTTP request resumes a retained computation, it uses that computation’s private database. A request supplying different source cannot resume it.

Execution and memory limits are deployment policies. Exhaustion uses the common formal errors stated above, independently of the host engine. If a failure prevents a usable protocol response, the connection may close; this does not establish whether remote work completed. Per-request budgets, continuation retention and cleanup after transport failure must not silently alter the documented paging or answer contract.

Deployment guides document resource accounting, source-fetch machinery, continuation storage and cleanup mechanisms. Protocol negotiation, wire envelopes, terminal acknowledgements and session replay are specified with the transport interfaces rather than as additional language predicates.
