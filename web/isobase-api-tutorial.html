Lab 1: one query is one complete HTTP request

Ask Prolog to split a list. The portal requests one solution at offset zero:

?- append(Xs,Ys,[a,b,c]).

Find these two highlighted Logger rows

  1. Request: API · STATELESS HTTP with GET /call.
  2. Response: a JSON event whose type is success.

The readable request is equivalent to:

GET /call?goal=append(Xs,Ys,[a,b,c])&offset=0&limit=1&format=json
{
  "type": "success",
  "data": [{ "Xs": "[]", "Ys": "[a,b,c]" }],
  "more": true
}
FieldMeaning
goalThe Prolog goal to run. Real URLs percent-encode this text; the Logger decodes it for readability.
offsetHow many solutions to skip before returning this slice.
limitMaximum solutions in the response.
formatThe requested result representation; the portal uses JSON.
src_textOptional source that belongs only to this request.

The most important missing field is a PID. Nothing in the response gives the client an address for a retained computation.

Lab 2: the next answer repeats the whole call

While the terminal offers another solution, use the button below. It operates the same Next action as the terminal.

GET /call?goal=append(Xs,Ys,[a,b,c])&offset=1&limit=1&format=json
{
  "type": "success",
  "data": [{ "Xs": "[a]", "Ys": "[b,c]" }],
  "more": true
}

Compare the two request rows

  • The complete goal appears again.
  • offset advances from 0 to 1.
  • No continuation command or PID appears.
  • Stop is local bookkeeping in ISOBASE; it does not need a protocol request.

A node may cache search work internally, but that cache is deliberately invisible. The public meaning of the second URL does not depend on reaching the same retained session.

Source text belongs to the request

A stateless client can supply temporary code, but it must send that code with every call that needs it:

const params = new URLSearchParams({
  goal: "double(21, X)",
  src_text: "double(A, B) :- B is A * 2.",
  offset: "0",
  limit: "1",
  format: "json"
});

The source is not installed into a private database for later calls. Shared node knowledge may of course change independently, so “replayable request” describes the protocol boundary rather than promising identical answers in the presence of time, randomness or changing shared data.

Learn the response vocabulary

typeInterpretationClient action
successdata contains zero or more binding rows; more says whether another slice may exist.Render rows, and offer Next when appropriate.
failureThe goal has no solution in this slice.Present ordinary Prolog failure.
errorThe goal, profile, sandbox or request was rejected, or execution raised an exception.Show the returned diagnostic; do not treat it as transport failure.
timeoutThe server-enforced execution limit was reached.Report bounded termination; retry only when application semantics permit it.
No remote Abort command exists. Cancelling a browser fetch can stop the browser waiting, but it is not an ISOBASE control message addressed to a retained server computation. Server time and resource limits remain essential.

A robust JavaScript client

async function call(goal, { offset = 0, limit = 1, source = "" } = {}) {
  const url = new URL("/call", location.origin);
  url.search = new URLSearchParams({
    goal,
    offset: String(offset),
    limit: String(limit),
    format: "json",
    ...(source ? { src_text: source } : {})
  });

  const response = await fetch(url, {
    headers: { Accept: "application/json" }
  });
  const event = await response.json();

  if (!response.ok || event.type === "error") {
    throw new Error(event.data || `HTTP ${response.status}`);
  }
  return event;
}

Keep transport errors, protocol errors and ordinary Prolog failure distinct; applications usually present and retry them differently.

Retries, caching and operational fit

  • Requests are self-contained, so load balancers do not need session affinity.
  • GET makes request identity visible, but caches should still respect authentication, headers and node policy.
  • Retry only computations whose application-level effects and external dependencies make retry safe.
  • Large goals and source text are subject to node input limits; expensive searches are subject to time and resource limits.

Choose ISOBASE for function-like search, validation, transformation and inference. Move to ISOTOPE when separate calls need a private database, retained continuation, interactive I/O or an addressable Abort operation.
