The ISOBASE mental model

Think of an ISOBASE call as a function with relational results:

request(goal, temporary_source, application_data)
    → solutions | failure | error | timeout

The node may use shared knowledge while answering, but it does not give the client a private process or database. Everything needed specifically for the computation must arrive with the request. Begin with the query used throughout the profile path:

?- append(Xs,Ys,[a,b,c]).
Observe. The first solution is Xs = [], Ys = [a,b,c]. Further solutions split the same list at later positions. ISOBASE has ordinary nondeterministic Prolog; stateless does not mean deterministic.

A self-contained rules service

ISOBASE can run client-supplied Prolog, provided the source accompanies every request that needs it. Select this small basket program as the temporary source for the tutorial calls:

valid_item(item(Name, Price)) :-
    atom(Name),
    number(Price),
    Price >= 0.

valid_basket(Items) :-
    maplist(valid_item, Items).

basket_total([], 0).
basket_total([item(_, Price)|Items], Total) :-
    basket_total(Items, Rest),
    Total is Price + Rest.

step(Items, add(Name, Price), [item(Name, Price)|Items]) :-
    valid_item(item(Name, Price)).
step(Items, remove(Name), Rest) :-
    select(item(Name, _), Items, Rest).

Now validate and total a complete input value:

?- Items = [item(tea,4),item(bread,3),item(cheese,8)],
   valid_basket(Items),
   basket_total(Items, Total).
Expect. Total = 15. The rules and data form one self-contained computation. The selected source is sent with the stateless call; it is not installed in a session for later use without being sent again.

Make application state explicit

Stateful applications are still possible; the state belongs to the application rather than an implicit Prolog session. Thread it through the relation as an input and an output:

?- State0 = [item(tea,4)],
   step(State0, add(bread,3), State1),
   step(State1, add(cheese,8), State2),
   basket_total(State2, Total).
Expect. State2 contains all three items and Total = 15. A web application can store that returned state in a database, cookie or subsequent request. ISOBASE itself retains none of it.

This explicit form is often easier to test and replay: the same rules can be applied to a saved state without first reconstructing a server session.

Search and paging without a continuation

Relational code can describe several valid next states:

?- step([item(tea,4),item(bread,3),item(cheese,8)],
        remove(Name), Rest).

Use ;, the space bar or Next to see each removable item. Unlike ISOTOPE, Next does not resume a retained Prolog stack. The client repeats the self-contained goal and source with a larger solution offset.

Programming consequence. Do not let one result page depend on invisible changes made by an earlier page. Search predicates are clearest when their solutions depend only on explicit request data and shared read-only knowledge.

Three kinds of knowledge

KnowledgeLifetime and role
Shared node databaseMaintained by the node owner and visible to authorized calls. It may change independently of the client.
Temporary request sourcePredicates sent with the current call, such as the basket program. They disappear at the request boundary.
Application dataTerms supplied in the goal and returned in solutions. The application decides whether and where to retain them.

“Stateless” describes the client-visible execution boundary. It does not promise mathematical purity: time, randomness, changing shared knowledge or external services can still make replay produce a different answer. Retries and caching are safe only when the application semantics permit them.

The deliberate boundary

Try one representative session operation:

?- assertz(saved(isobase)).
Expect a profile violation. Dynamic updates, interactive input and output, independent actors, mailboxes and client-addressable Abort all require a retained execution context and are outside ISOBASE.

Timeout instead of Abort

The following goal deliberately does not terminate. N1 has no Abort button because there is no retained pid or separate control channel to address:

?- repeat, fail.

The node ends it at its configured request limit. Cancelling a browser request may stop the browser waiting, but it is not a remote Abort command.

When to choose ISOBASE

Choose ISOBASE when the computation is naturally described by explicit inputs, temporary rules and relational results. Its main advantages are:

  • a small, self-contained request/response contract;
  • no client session state to retain or recover;
  • straightforward replay, caching and load balancing; and
  • clear server-enforced time and resource bounds.

It is a good fit for search, validation, transformation, parsing, rules evaluation and inference. The profile also includes the stateless remote-programming predicates rpc/2-3, promise/3-4 and yield/2-3.

Move to ISOTOPE when several calls need a private database, a retained search, interactive I/O or addressable Abort. Move to ACTOR when independently running processes must initiate messages or supervise one another.

You should now be able to explain: why temporary source is still useful on a stateless node; how to thread application state through a relation; why Next can work without a continuation pid; and why stateless transport is not the same thing as pure computation.
