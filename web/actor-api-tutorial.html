The ACTOR API

A short tour of Web Prolog's stateful WebSocket protocol. Commands travel in both directions over one live connection, and the server can speak first.

Open one bidirectional channel

const socket = new WebSocket("wss://node.example/ws");

Once it opens, send a spawn command as JSON:

{ "command": "toplevel_spawn",
  "options": "[session(true),src_text('q(X):-p(X).')]" }
{ "type": "spawned", "pid": 4384261893 }

The same query, now as WebSocket messages

?- append(Xs,Ys,[a,b,c]).

{
  "command": "toplevel_call",
  "pid": 4384261893,
  "goal": "append(Xs,Ys,[a,b,c])",
  "options": "[limit(1)]"
}
{
  "type": "success",
  "pid": 4384261893,
  "data": [{ "Xs": "[]", "Ys": "[a,b,c]" }],
  "more": true
}

Ask for the continuation on the same socket:

{ "command": "toplevel_next", "pid": 4384261893 }
{
  "type": "success",
  "pid": 4384261893,
  "data": [{ "Xs": "[a]", "Ys": "[b,c]" }],
  "more": true
}

What push changes

Answers, output, prompts and monitor events arrive as soon as the node emits them; no /toplevel_poll round trip is needed. Events from several actors may be interleaved on one connection, so clients route them by pid and type.

The toplevel has the same private state as ISOTOPE, while the ACTOR profile additionally exposes actor creation, messaging, monitoring and links.

Select API traffic in the Logger before pressing CALL. On a remote ACTOR node, the entries are the actual JSON messages carried by the stateful WebSocket.

For executable browser code, compare the WebSocket toplevel demo and the actor messaging demo.

WebSocket versus SWI-WASM

In SWI-WASM Worker mode there is no network WebSocket. The browser UI sends the same command vocabulary to a Web Worker as JavaScript objects, using the structured-clone mechanism; replies return as JavaScript event objects. The Logger therefore shows STATEFUL WORKER · JS OBJECT. This is the real carrier used there, not JSON styled to look like WebSocket traffic.

Advantages and disadvantages

AdvantagesDisadvantages
Low-latency push; mixed-initiative interaction; several actors can share one connection; access to the full concurrent actor model. A persistent connection must be opened, monitored and re-established; clients must handle routing, ordering, disconnect semantics and back-pressure.

Choose ACTOR for reactive or concurrent applications where either side may initiate activity. Prefer ISOBASE for independent function-like calls, or ISOTOPE when session state is needed but HTTP polling is sufficient.
