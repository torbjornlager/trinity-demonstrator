Open one bidirectional channel

const protocol = location.protocol === "https:" ? "wss:" : "ws:";
const socket = new WebSocket(`${protocol}//${location.host}/ws`);

After the WebSocket opens, both directions carry JSON objects. The client sends objects with a command; the node emits objects with a type.

// client → node
{
  "command": "toplevel_call",
  "pid": PID,
  "goal": "member(X,[a,b,c])",
  "options": "[limit(1)]"
}
// node → client
{
  "type": "success",
  "pid": PID,
  "data": [{ "X": "a" }],
  "more": true
}

There is no HTTP request/response pairing after the upgrade. A client correlates activity using pid, type and its own knowledge of outstanding operations.

Lab 1: drive a persistent toplevel

A fresh portal connection creates a long-lived toplevel:

{
  "command": "toplevel_spawn",
  "options": "[session(true)]"
}
{ "type": "spawned", "pid": PID_FROM_SPAWN }
?- append(Xs,Ys,[a,b,c]).

Trace the real PID

  1. On a fresh connection, find toplevel_spawn followed by spawned.
  2. Find toplevel_call and its success event with the same PID.
  3. Next sends toplevel_next without repeating the goal.
  4. Stop sends toplevel_stop, discarding only the current continuation.

If a toplevel already existed, the portal correctly starts at step 2.

Lab 2: observe what push removes

Output arrives without polling

?- writeln('pushed over the live carrier').

What not to find

The node emits an output event and then a final event. There is no /toplevel_poll request between them: the open carrier already gives the node a route back to the browser.

A prompt is another pushed event

?- read(Term), writeln(Term).

Enter a complete term ending with a full stop when the terminal shows |:. The shell's standard read/1 is implemented over the actor prompt protocol. The Logger shows prompt arriving, toplevel_respond leaving, then subsequent output and completion arriving immediately.

toplevel_call → prompt
toplevel_respond → output → success

Lab 3: use the actor API itself

A separate WebSocket can own actors without creating a toplevel. This lab opens such a connection, spawns an echo actor, sends two messages, observes two unsolicited outputs and exits the actor. Every actual frame is mirrored into the portal Logger and highlighted.

Ready. This lab requires a remote ACTOR node with a stateful WebSocket.
// 1. Create an independently running actor.
{
  "command": "spawn",
  "goal": "echo_actor",
  "options": "[src_text(\"echo_actor :- ...\")]"
}

// 2. Address it by the PID returned in the spawned event.
{ "command": "send", "pid": ACTOR_PID, "message": "msg(first)" }
{ "command": "send", "pid": ACTOR_PID, "message": "msg(second)" }

// 3. End it explicitly.
{ "command": "exit", "pid": ACTOR_PID, "reason": "done" }

Read the interleaving

The two send commands do not synchronously return values. Later output events identify the actor by PID. This is message-passing concurrency, not a sequence of function calls disguised as JSON.

CommandTypical event or effect
spawnspawned returns a new actor PID.
sendPlaces a Prolog term in an actor mailbox; later events are independent.
exitRequests actor termination; monitors or owners can observe down.
monitoring and linksTurn lifecycle changes into asynchronous notifications and failure propagation.

The actor messaging demo expands this pattern into a browser subscriber for a node-resident publish/subscribe service.

Multiplexing changes the client architecture

Events for a toplevel, child actors, monitors and services may be interleaved on one connection. Use one dispatcher rather than assigning socket.onmessage afresh for each request:

const actors = new Map();
const pendingSpawns = [];

socket.addEventListener("message", ({ data }) => {
  const event = JSON.parse(data);

  if (event.type === "spawned" && pendingSpawns.length) {
    pendingSpawns.shift()(event);
    return;
  }

  const handler = actors.get(String(event.pid));
  if (handler) handler(event);
  else console.warn("unrouted event", event);
});

A production router should keep request correlation separate from actor ownership, tolerate events it does not understand, and remove routes when actors terminate.

The command vocabulary and lifecycle concepts are deliberately parallel, but the carrier is real and should not be disguised. A JavaScript object shown for Worker mode is not JSON traffic pretending to have crossed a WebSocket.

The raw actor lab above intentionally requires the WebSocket track. In Worker mode, use the terminal exercises: the Logger will show the corresponding Worker envelopes generated by the portal.

A small resilient WebSocket client

function openActorChannel() {
  const url = new URL("/ws", location.href);
  url.protocol = url.protocol === "https:" ? "wss:" : "ws:";
  const socket = new WebSocket(url);
  const routes = new Map();

  socket.addEventListener("message", ({ data }) => {
    let event;
    try { event = JSON.parse(data); }
    catch (error) { return console.error("invalid frame", error); }

    const route = routes.get(String(event.pid));
    if (route) route(event);
    else handleConnectionEvent(event);
  });

  socket.addEventListener("close", () => {
    for (const route of routes.values()) {
      route({ type: "disconnected" });
    }
    routes.clear();
  });

  return {
    socket,
    route(pid, handler) { routes.set(String(pid), handler); },
    send(command) {
      if (socket.readyState !== WebSocket.OPEN) {
        throw new Error("actor channel is not open");
      }
      socket.send(JSON.stringify(command));
    }
  };
}

Authentication and same-origin policy apply during connection setup. Treat malformed frames, unknown PIDs and disconnects as protocol states, not exceptional cases that can be ignored.

Disconnect, reconnection and back-pressure

  • A closed socket destroys the browser's delivery route. Do not assume that replaying every old command is safe.
  • Re-establish the connection, recreate the required toplevels or actors, and rebuild routing tables explicitly.
  • Bound client-side queues and render work. A producer that can push faster than the browser consumes needs application-level flow control.
  • Stop continuations and halt or exit owned processes during orderly shutdown; monitors help discover unexpected termination.

Choose ACTOR for reactive, concurrent or mixed-initiative applications. Prefer ISOTOPE when one retained toplevel is sufficient and HTTP polling is operationally simpler; prefer ISOBASE for independent function-like computations.
