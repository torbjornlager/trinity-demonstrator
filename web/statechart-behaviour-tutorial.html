Web Prolog tutorial – the statechart behaviour

Statecharts turn an ACTOR process into an explicit hierarchical state machine. Events still arrive through an ordinary actor mailbox, while states, transitions, guards and history organize the control logic.

Before you begin. Use SWI-WASM or an ACTOR node such as N3 or N4. Work through the core ACTOR tutorial first if pids, send and receive are unfamiliar. Each spawned statechart returns Pid; later buttons use the terminal's remembered $Pid binding.

The behaviour model

A statechart actor is still an actor: statechart_spawn/2 returns a pid, other actors send it terms, and monitors can observe its termination. The behaviour changes how one actor interprets its mailbox.

message arrives → matching transition is selected → source states exit
↓
transition action runs → target states enter → stable configuration waits
ConstructPurpose
<state>Names a control situation; nesting expresses hierarchy.
<parallel>Keeps several regions active at the same time.
<go on="...">Matches an event and may change the active configuration.
if="Goal"Uses a Prolog guard to decide whether a transition is enabled.
<history>Remembers a previous nested configuration for later re-entry.
Transition bodyRuns Web Prolog code: update data, call relations, send messages or spawn helpers.

When several transitions could react, selection follows the statechart semantics rather than source-code clause order. The active configuration and event queue therefore matter as much as the incoming term.

Lab 1: hierarchy and history

The pause-and-resume chart contains a play state with nested states s1 and s2, plus an interrupted sibling. Pausing leaves play; resuming enters its history target and returns to whichever nested state was active.

Every compound state names its default child with the initial attribute. SXML does not infer an initial state from the first child.

<state id="game" initial="play">
    <state id="play" initial="s1">
        <history id="h">
            <go to="s1"/>
        </history>
        <state id="s1">
            <go to="s2" on="play"/>
        </state>
        <state id="s2">
            <go to="s1" on="reset"/>
        </state>
        <go to="interrupted" on="pause"/>
    </state>
    <state id="interrupted">
        <go to="h" on="resume"/>
    </state>
</state>
?- statechart_spawn(Pid, [
       src_uri('/examples/statecharts/01%20pause-and-resume.xml')
   ]).

Lab 2: read a tangled chart systematically

A large statechart is easier to read in three passes: identify top-level regions, find their initial leaf states, then follow only transitions whose source contains an active leaf. Ignore the rest until the configuration changes.

?- statechart_spawn(Pid, [
       src_uri('/examples/statecharts/02%20spaghetti.xml')
   ]).

Explore all eight events, a through h, and watch the active leaf and highlighted transition after every send. Try the same event again after the active leaf changes: the same event name can select a different transition because its source state differs. An event with no enabled transition leaves the configuration unchanged. Event h reaches the final state only from s211; spawn the chart again if you want to continue experimenting afterward.

Lesson. An event does not name a global jump. It offers a term to the current configuration; only enabled transitions rooted in active states can consume it.

Lab 3: one event can affect parallel regions

The emotions example models orthogonal dimensions of an NPC at the same time. One region tracks anger/fear, another anticipation/surprise, and a third attacking/fleeing.

?- statechart_spawn(Pid, [
       src_uri('/examples/statecharts/03%20emotions.xml')
   ]).
EventParallel effects
eMoves toward fear, surprise and fleeing in the regions that enable it.
dMoves fear toward anger and fleeing toward attacking.
fMoves surprise toward anticipation.

Parallel regions are useful when flattening every combination into states such as angry_surprised_attacking would cause a combinatorial explosion.

This chart has no final state or application-level stop event, so it remains alive after the experiment. Halt it before moving to the next lab:

?- statechart_halt($Pid, Reply, 1).
Observe. The bounded call returns after the chart acknowledges the stop. If it cannot acknowledge within one second, the runtime terminates it instead of leaving the toplevel waiting indefinitely.

Lab 4: Computing the GCD

Web Prolog can serve as a scripting language inside statecharts. Executable Web Prolog code in transition bodies and guards increases their power significantly: a chart can update data, run relations, produce output, and still keep the surrounding control logic explicit.

The statechart below applies Euclid's algorithm to find the greatest common divisor of a list of integers. The machine has two states: init waits for a single integers/1 event carrying the list, then run iterates — repeatedly replacing the larger of any two values with their difference — until only one value remains and the result is printed. 

<statechart version="0.2" initial="init">
    <datamodel>
        :- dynamic int/1.
    </datamodel>
    <state id="init">
        <go on="integers(List)" to="run">
            forall(member(X, List), asserta(int(X)))
        </go>
    </state>
    <state id="run">
        <go if="int(X), int(Y), X > Y">
            Z is X-Y,
            retract(int(X)),
            assert(int(Z))
        </go>
        <go to="stop" if="int(X)">
            writeln(X)
        </go>
    </state>
    <final id="stop" />
</statechart>

?- statechart_spawn(Pid, [
       src_uri('/examples/statecharts/08%20gcd.xml')
   ]).
?- $Pid ! integers([25,10,15,30]).
Expect. The chart prints 5 and reaches its final state. Guards decide when an internal step is enabled; transition bodies update the private Prolog datamodel.

Lab 5: invoke and coordinate another process

Statecharts become more useful once they can spawn other processes and communicate with them. In Web Prolog, the invoked processes are simply actors: toplevels, other statechart actors, or services running on local or remote nodes.

This final example spawns a child toplevel, submits a query to it, prints each answer as it arrives, and terminates when the last answer has been received. The spawned toplevel is initialized with a small program: q(X) :- p(X) and four facts, p(a) through p(d). 

<statechart version="0.2" initial="spawn-ask-collect">
    <state id="spawn-ask-collect" initial="ask">
        <spawn type="toplevel" options="[time_limit(30)]">
            q(X) :- p(X).
            p(a). p(b). p(c). p(d).
        </spawn>
        <state id="ask">
            <go to="collect" on="spawned(Pid)">
                toplevel_call(Pid, q(X), [
                    limit(1)
                ])
            </go>
        </state>
        <state id="collect">
            <go to="collect" on="success(Pid, Data, true)">
                writeln(Data),
                toplevel_next(Pid)
            </go>
            <go to="final" on="success(_, Data, false)">
                writeln(Data)
            </go>
        </state>
    </state>
    <final id="final" />
</statechart>
?- statechart_spawn(Pid, [
       src_uri('/examples/statecharts/10%20spawn-toplevel.xml')
   ]).

When the surrounding state becomes active, the <spawn> element creates the child toplevel. The generated spawned(Pid) event reports the pid of that child actor, and the transition from ask to collect calls toplevel_call/3 with limit(1).

Each answer arrives as success(Pid, Data, More). While More is true, the chart prints the current answer and asks the child toplevel for the next one with toplevel_next/1. When More is false, the last answer has arrived and the machine enters its final state.

Variables bound by the on pattern, and by any if guard, are in scope in the executable content of the same <go> element. The intent of <spawn> is also ownership: the helper process belongs to the control state that created it, so leaving that state can clean up the invoked actor without ad hoc shutdown code.

Design and lifecycle guidance

  • Use hierarchy to factor transitions shared by several substates.
  • Use parallel regions only for genuinely independent dimensions.
  • Keep transition guards observational where possible; put updates in transition bodies.
  • Define what happens to unexpected events: ignore, defer, report or handle them in an ancestor state.
  • Give invoked actors an ownership scope and a termination path.
  • Monitor long-lived charts when another process must react to failure.
