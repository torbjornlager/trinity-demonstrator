The ISOTOPE API

A guided lab for Web Prolog's semi-stateful HTTP protocol. Ordinary POST requests address one persistent toplevel session, while the browser remains responsible for every exchange.

Lab 1: create and address a private toplevel

The first interactive call in a fresh portal session starts with:

POST /toplevel_spawn
Content-Type: application/json

{ "options": "[session(true)]" }
{ "type": "spawned", "pid": PID_FROM_SPAWN }

Do not copy a PID from documentation: it is allocated at runtime. The next exercise highlights the real PID returned to your browser.

?- append(Xs,Ys,[a,b,c]).

What to find in the Logger

  1. On a fresh session, POST /toplevel_spawn and a spawned event appear first.
  2. POST /toplevel_call carries the returned PID, goal and answer limit.
  3. The success event repeats the same PID and reports more: true.

If the portal already had an ISOTOPE session, the spawn pair is correctly absent: the call reuses the existing PID.

POST /toplevel_call
Content-Type: application/x-www-form-urlencoded

pid=PID_FROM_SPAWN&goal=append(Xs,Ys,[a,b,c])&limit=1&format=json
{
  "type": "success",
  "pid": PID_FROM_SPAWN,
  "data": [{ "Xs": "[]", "Ys": "[a,b,c]" }],
  "more": true
}

Lab 2: continue, then stop, the retained search

The continuation lives inside the toplevel. Next therefore sends only its address:

POST /toplevel_next
Content-Type: application/x-www-form-urlencoded

pid=PID_FROM_SPAWN&format=json

Compare the highlighted requests

  • toplevel_next does not repeat the goal or source.
  • The PID stays constant.
  • toplevel_stop discards the current continuation but keeps the session and its private database alive.

This is the central difference from ISOBASE paging: ISOTOPE resumes retained execution state rather than describing a fresh offset into the search.

Lab 3: prove that database state survives separate calls

These must be two calls. The first updates the session-local database; the second reads it:

?- assertz(saved(api)).
?- saved(What).

What the Logger proves

Both toplevel_call requests use the same PID. The source and goal differ, but the second call sees the first call's update. A different client session would receive another PID and another private database.

StateLifetime
Private predicates and dynamic factsAcross separate calls, until the session is halted or reclaimed.
Current answer continuationUntil exhausted, stopped, aborted or replaced by another call.
Output, prompt and trace eventsQueued for the client to retrieve because HTTP cannot push them spontaneously.
Remembered portal bindingsClient-side convenience associated with this terminal session.

Lab 4: output and prompts require HTTP choreography

Output

?- writeln('Hello over semi-stateful HTTP').

The initial call may return an output event. The portal then issues /toplevel_poll until it reaches the final success, failure, error or prompt. The highlighted rows show every round trip.

Prompt and response

?- read(Term), writeln(Term).

When the terminal changes to the |: prompt, enter a complete Prolog term ending with a full stop. ISOTOPE exposes the standard read/1 interaction; the lower-level actor input/2-3 primitive belongs to ACTOR. Watch the Logger sequence:

toplevel_call → output → toplevel_poll → prompt
toplevel_respond → responded → toplevel_poll → output → toplevel_poll → success

The exact number of polls depends on the events produced. That variability is why clients should route by event type, not assume a fixed response count.

Stop, abort and halt solve different problems

EndpointWhat endsWhat survives
/toplevel_stopThe pending answer continuation.The session, private database and ability to make another call.
/toplevel_abortThe currently running or waiting computation.The session can accept later calls.
/toplevel_haltThe whole toplevel session.Nothing addressed by that PID; server resources are released.
Compatibility note: older deployed nodes may not yet provide /toplevel_halt. If it returns 404, use /toplevel_abort to end active work; the idle session then remains until the server reclaims it. Current nodes should use Halt for deterministic release.
?- repeat, fail.
The node also enforces a timeout, so a short configured timeout may win the race before you press Abort. Both outcomes are valid and visible in the Logger.

Complete endpoint map

EndpointRole
POST /toplevel_spawnCreate a session and load canonical src_* options.
POST /toplevel_callStart a goal in the session.
POST /toplevel_nextResume its answer continuation.
POST /toplevel_pollRetrieve the next queued event.
POST /toplevel_respondSupply a Prolog term to a pending prompt.
POST /toplevel_stopDiscard continuation state.
POST /toplevel_abortInterrupt active work.
POST /toplevel_haltTerminate the session.

All session operations use POST because they create, consume or mutate persistent state. Form-encoded request bodies are canonical; spawn additionally accepts a JSON body.

A small JavaScript session client

async function postForm(path, fields) {
  const response = await fetch(path, {
    method: "POST",
    headers: {
      Accept: "application/json",
      "Content-Type": "application/x-www-form-urlencoded"
    },
    body: new URLSearchParams(fields)
  });
  const event = await response.json();
  if (!response.ok || event.type === "error") {
    throw new Error(event.data || `HTTP ${response.status}`);
  }
  return event;
}

const spawned = await fetch("/toplevel_spawn", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ options: "[session(true)]" })
}).then(response => response.json());

try {
  const first = await postForm("/toplevel_call", {
    pid: spawned.pid,
    goal: "member(X,[a,b,c])",
    limit: "1",
    format: "json"
  });
  // Route first.type, then use next/poll/respond as required.
} finally {
  try {
    await postForm("/toplevel_halt", {
      pid: spawned.pid,
      format: "json"
    });
  } catch (_olderNode) {
    await postForm("/toplevel_abort", {
      pid: spawned.pid,
      format: "json"
    });
  }
}

A real client should centralize event routing, reject replies for an unexpected PID, and halt abandoned sessions in cleanup paths. A compatibility fallback to Abort interrupts work but does not release an older node's session immediately.
